# GEMM AVX2/AVX-512 版本性能分析报告

---

## 一、测试环境

| 项目 | 说明 |
|------|------|
| **平台** | Linux (Ubuntu) |
| **CPU** | Intel(R) Xeon(R) Silver 4210 CPU @ 2.20GHz |
| **核心数** | 10 物理核心 / 20 逻辑核心 |
| **最大睿频** | 3.2 GHz |
| **L1 数据缓存** | 32 KB / 核心 |
| **L2 缓存** | 1 MB / 核心 |
| **L3 缓存** | 14 MB 共享 |
| **架构** | x86-64 (Cascade Lake) |
| **SIMD支持** | SSE, SSE2, AVX, AVX2, AVX-512F/DQ/BW/VL |

**理论峰值计算**：

> FMA 指令一次完成乘法和加法，计为 2 FLOPs。每个核心有 2 个 FMA 执行单元。

- AVX2 (256位, 4 doubles): 4 doubles × 2 FMA × 2 FLOPs × 3.2 GHz = **51.2 GFLOPS**（单核心）
- AVX-512 (512位, 8 doubles): 8 doubles × 2 FMA × 2 FLOPs × 3.2 GHz = **102.4 GFLOPS**（单核心）

> **注意**：实际运行时，AVX-512 指令会导致 CPU 降频（约降至 1.0-2.2 GHz），因此 AVX-512 实际峰值约为 **32-70.4 GFLOPS**。

## 二、测试参数修改

### 2.1 parameters.h 修改内容

| 参数 | 原值 | 新值 | 说明 |
|------|------|------|------|
| `PFIRST` | 100 | **64** | 最小矩阵维度 |
| `PLAST` | 1000 | **1280** | 最大矩阵维度 |
| `PINC` | 100 | **64** | 步长 |

### 2.2 修改原因与好处

**原因**：AVX-512 微内核的列数（NR）为 8/16/32，100 不是这些数的整数倍，导致边界处理时缓冲区溢出。

**好处**：
1. **消除边界问题**：64 是 4、8、16、32 的公倍数，所有微内核版本无需边界处理代码
2. **更精细的性能曲线**：步长 64 比 100 更小，可以观察更多数据点
3. **更大矩阵测试**：1280 比 1000 大，可以看到大矩阵的缓存效应

## 三、版本修改分析

### 3.0 MMult0（基线版本）

**实现方式**：三重循环朴素矩阵乘法（i, j, p 循环）

**性能结果**：**1.51 GFLOPS**

---

### 3.1 MMult4-4x4-avx2.c（AVX2 版本，4行×4列）

**主要修改**（相对于 MMult3_4x4_15）：
- 使用 AVX2 指令集（`__m256d`，256位向量）
- 每次处理 4×4 的微内核
- 使用 `_mm256_loadu_pd` / `_mm256_storeu_pd` 加载/存储
- 分块参数：nc=128, kc=256

**性能提升原因**：
- AVX2 可同时处理 4 个 double，是 SSE2（128位）的 2 倍
- 打包 A 和 B 矩阵，提高缓存利用率

**性能结果**：**21.65 GFLOPS**（达到 AVX2 理论峰值的 **42.3%**）

---

### 3.2 MMult4-4x8-avx2.c（AVX2 版本，4行×8列）

**主要修改**（相对于 4×4 AVX2 版本）：
- 微内核从 4×4 扩展到 4×8
- 使用 FMA 指令（`_mm256_fmadd_pd`）替代乘加分离
- 直接加载/存储 C 矩阵（避免逐个元素提取）
- 动态分配打包内存（`aligned_alloc`），支持任意矩阵大小
- 分块参数：nc=128, kc=256

**性能提升原因**：
- 4×8 微内核每次循环计算 32 个元素（vs 4×4 的 16 个），数据复用率翻倍
- FMA 指令将乘法和加法合并为一条指令，减少指令数约 50%
- 直接加载/存储 C 矩阵避免了大量的逐个元素提取和累加操作
- 动态内存分配消除了栈溢出风险

**性能结果**：**34.97 GFLOPS**（达到 AVX2 理论峰值的 **68.3%**）

---

### 3.3 MMult4-4x8-avx512.c（AVX-512，4行×8列）

**主要修改**（相对于 AVX2 4×8 版本）：
- 使用 AVX-512 指令集（`__m512d`，512位向量）
- 使用 `_mm512_fmadd_pd`

**性能结果**：**21.41 GFLOPS**

> **注意**：AVX-512 版本性能低于 AVX2 版本，原因见第六章分析。

---

### 3.4 MMult4-8x8-avx512.c（AVX-512，8行×8列）

**主要修改**（相对于 4×8 版本）：
- 微内核从 4×8 扩展到 8×8
- 行方向处理 8 行，需要更多寄存器

**性能提升原因**：
- 8×8 微内核每次循环计算 64 个元素（vs 4×8 的 32 个），数据复用率翻倍

**性能结果**：**25.08 GFLOPS**

---

### 3.5 MMult4-4x16-avx512.c（AVX-512，4行×16列）

**主要修改**（相对于 4×8 版本）：
- 微内核从 4×8 扩展到 4×16
- 使用两个 `__m512d` 处理 16 列

**性能提升原因**：
- 16列宽度充分利用AVX-512向量，减少循环次数

**性能结果**：**26.38 GFLOPS**

---

### 3.6 MMult4-4x16-avx512a.c（AVX-512，堆分配版本）

**主要修改**（相对于栈分配版本）：
- packedB 使用 `aligned_alloc` 动态分配（64字节对齐）
- 支持任意大小的内存需求

**性能结果**：**12.83 GFLOPS**

> **说明**：堆分配版本性能显著下降，可能由于内存分配开销和缓存不友好。

---

### 3.7 MMult4-4x32-avx512.c（AVX-512，4行×32列）

**主要修改**（相对于 4×16 版本）：
- 微内核从 4×16 扩展到 4×32
- 使用 4 个 `__m512d` 处理 32 列
- 编译器自动优化为 FMA 指令
- 动态内存分配
- 分块参数：nc=64, kc=1024

**性能提升原因**：
- 32列宽度最大化向量利用率
- 4行高度保持较低寄存器压力

**性能结果**：**26.02 GFLOPS**

---

### 3.8 MMult4-4x32-avx512-nc128.c（AVX-512，nc=128）

**主要修改**（相对于 4×32 原版）：
- nc 从 64 增加到 128：更大的 B 矩阵分块，减少外层循环迭代次数
- 使用 `_mm512_fmadd_pd` 内联函数（显式 FMA）
- PackMatrixB 使用 AVX-512 加载/存储指令

**性能结果**：**24.93 GFLOPS**

> **说明**：nc=128 版本性能反而下降，可能因为 L2 缓存压力过大。

---

### 3.9 MMult4-8x16-avx512.c（AVX-512，8行×16列）

**主要修改**（相对于 8×8 版本）：
- 微内核从 8×8 扩展到 8×16
- 使用两个 `__m512d` 处理 16 列
- 8行高度需要更多累加器寄存器

**性能提升原因**：
- 16列宽度充分利用AVX-512向量
- 8行高度增加数据复用

**性能结果**：**24.18 GFLOPS**

---

### 3.10 MMult4-8x24-avx512.c（AVX-512，8行×24列）

**主要修改**（相对于 8×16 版本）：
- 微内核从 8×16 扩展到 8×24
- 使用三个 `__m512d` 处理 24 列
- 分块参数：nc=72, kc=512

**性能结果**：**13.46 GFLOPS**

> **说明**：性能严重下降，原因是寄存器溢出——8行×24列需要24个ZMM寄存器（8行×3个向量），超过CPU可用的32个寄存器限制，导致大量数据溢出到内存。

---

### 3.11 MMult4-9x16-avx512.c（AVX-512，9行×16列）

**主要修改**（相对于 8×16 版本）：
- 微内核从 8×16 扩展到 9×16
- 9行高度需要更多累加器寄存器
- 添加边界处理支持非8倍数行数

**性能结果**：**26.92 GFLOPS**

---

### 3.12 MMult4-10x16-avx512.c（AVX-512，10行×16列）

**主要修改**（相对于 9×16 版本）：
- 微内核从 9×16 扩展到 10×16
- 10行高度需要更多累加器寄存器

**性能结果**：**25.89 GFLOPS**

> 若考虑 AVX-512 降频后的实际峰值（~32 GFLOPS），9×16 版本达到约 **84.1%**。

### 4.2 性能提升关键因素

1. **向量宽度**：AVX-512 (512位) > AVX2 (256位) > SSE (128位)
2. **微内核大小**：更大的微内核 → 更多数据复用 → 更少内存访问
3. **FMA 指令**：将乘法和加法合并，减少指令数约 50%
4. **内存对齐**：对齐加载比非对齐加载快约 5-10%
5. **分块策略**：合理的 kc/nc 分块减少缓存失效
6. **直接加载/存储 C**：避免逐个元素提取，减少冗余操作
7. **寄存器压力**：过大的微内核会导致寄存器溢出，严重降低性能

## 五、小矩阵性能分析

### 5.1 现象

所有版本在小矩阵（如 64×64×64）时性能显著低于大矩阵。例如：
- MMult4-4x8-avx2：64×64 时 27.59 GFLOPS，1280×1280 时 34.97 GFLOPS（差距 1.3 倍）
- MMult4-9x16-avx512：64×64 时约 20 GFLOPS，1280×1280 时 26.92 GFLOPS（差距约 1.3 倍）

### 5.2 原因分析

1. **打包开销占比大**：小矩阵的打包成本（A 打包、B 打包）占总计算时间的比例更高。打包是 O(k×n) 操作，而计算是 O(m×n×k) 操作，小矩阵时打包占比显著增大。

2. **循环开销**：k 维度短时，内层循环迭代次数少，循环控制开销（分支预测、计数器更新）占比更高。

3. **缓存冷启动**：第一次访问数据时，数据不在缓存中，需要从内存加载。小矩阵的总计算量小，缓存预热成本无法被充分摊销。

4. **固定开销**：函数调用、内存分配（`aligned_alloc`/`free`）等固定开销在小矩阵时占比更高。

5. **分块颗粒度**：当前分块参数（如 kc=1024）针对大矩阵优化，小矩阵（如 k=64）无法充分利用分块的优势。

### 5.3 优化建议

- 对于小矩阵（k < 256），可以跳过打包步骤，直接使用朴素 SIMD 计算
- 动态调整分块参数：小矩阵使用更小的 kc/nc

## 六、AVX-512 性能瓶颈分析

### 6.1 为什么 AVX-512 版本性能不如 AVX2？

MMult4-4x8-avx2 达到 34.97 GFLOPS，而所有 AVX-512 版本最高仅 26.92 GFLOPS。主要原因：

1. **AVX-512 频率降频（核心原因）**：Intel Xeon Silver 4210 在执行 AVX-512 指令时，CPU 会显著降低时钟频率。通过 `/proc/cpuinfo` 实测：
   - 标称频率：2.20 GHz
   - 运行 AVX-512 时频率：约 **1.0 GHz**（降频约 55%）
   - 运行 AVX2 时频率：约 **2.2-3.2 GHz**
   
   频率下降幅度抵消了 AVX-512 的向量宽度优势：
   - AVX2 实际：~3.2 GHz × 4 × 2 × 2 = 51.2 GFLOPS
   - AVX-512 实际：~1.0 GHz × 8 × 2 × 2 = 32 GFLOPS

2. **寄存器压力**：8×24 微内核需要 24 个 ZMM 寄存器，超过 CPU 可用的 32 个寄存器限制，导致寄存器溢出到内存，性能严重下降（仅 13.46 GFLOPS）。

3. **功耗墙**：AVX-512 的功耗远高于 AVX2，Intel 的"license-based"频率管理策略导致 AVX-512 代码运行在更低的频率。

### 6.2 AVX-512 版本中哪个性能最好？为什么？

**MMult4-9x16-avx512 性能最好（26.92 GFLOPS）**

**原因分析**：

| 版本 | 微内核 | 寄存器需求 | 性能 | 分析 |
|------|--------|-----------|------|------|
| MMult4-4x8-avx512 | 4×8 | 4累加器 + 1B向量 = 5 | 21.41 | 列数太少，向量利用率低 |
| MMult4-8x8-avx512 | 8×8 | 8累加器 + 1B向量 = 9 | 25.08 | 行数增加，数据复用提升 |
| MMult4-4x16-avx512 | 4×16 | 4累加器 + 2B向量 = 6 | 26.38 | 列数翻倍，性能提升 |
| MMult4-4x32-avx512 | 4×32 | 4累加器 + 4B向量 = 8 | 26.02 | 列数过多，分块效率下降 |
| MMult4-8x16-avx512 | 8×16 | 8累加器 + 2B向量 = 10 | 24.18 | 行数过多，寄存器压力大 |
| MMult4-8x24-avx512 | 8×24 | 8累加器 + 3B向量 = 11 | 13.46 | **寄存器溢出** |
| **MMult4-9x16-avx512** | **9×16** | **9累加器 + 2B向量 = 11** | **26.92** | **最佳平衡** |
| MMult4-10x16-avx512 | 10×16 | 10累加器 + 2B向量 = 12 | 25.89 | 行数过多，边界开销 |

**关键结论**：9行×16列的微内核在向量宽度利用、数据复用和寄存器压力之间取得了最佳平衡。

### 6.3 CPU降频确认方法

```bash
# 查看CPU当前频率
cat /proc/cpuinfo | grep "cpu MHz" | head -1

# 监控频率变化（需要安装lm-sensors）
watch -n 1 "cat /proc/cpuinfo | grep 'cpu MHz' | head -1"

# 使用perf监控实际频率
perf stat -e cycles,instructions ./test_MMult.x
```

**实测结果**：
- 空闲时：~1000 MHz（节能模式）
- 运行AVX2时：~2200-3200 MHz
- 运行AVX-512时：~1000 MHz

### 6.4 带宽瓶颈确认方法

**计算强度分析**：
- GEMM计算强度 = 2MNK / (MN + NK + MK) × sizeof(double)
- 对于1280×1280矩阵：计算强度 ≈ 106.7 FLOPS/byte

**当前是否存在带宽瓶颈**：

1. **不同微内核配置性能差异大**：如果计算单元是瓶颈，不同配置的性能应该更接近
2. **8x24版本异常低**：说明内存访问模式对性能影响显著
3. **nc参数调整效果有限**：nc128版本性能反而下降

**确认方法**：

```bash
# 使用stream基准测试内存带宽
wget https://www.cs.virginia.edu/stream/FTP/Code/stream.c
gcc -O2 -march=native stream.c -o stream
./stream

# 使用perf工具分析
perf stat ./test_MMult.x
perf record ./test_MMult.x
perf report
```

### 6.5 如何进一步提升

1. **混合指令策略**：在 AVX-512 代码中适当混入 AVX2 或 SSE 指令，可能减轻降频程度
2. **多核并行**：当前测试使用单核心，10 核心并行可将性能提升近 10 倍
3. **缓存预取**：使用 `_mm_prefetch` 在计算前预取数据，隐藏内存延迟
4. **更优分块参数**：针对不同矩阵大小动态选择最优的 kc/nc
5. **使用 MKL/BLIS**：Intel MKL 或 BLIS 库经过深度优化，可达到 80%+ 的理论峰值

## 八、结论

1. **最佳 AVX2 版本**：MMult4-4x8-avx2，达到 **34.97 GFLOPS**（68.3% AVX2 理论峰值）
2. **最佳 AVX-512 版本**：MMult4-9x16-avx512，达到 **26.92 GFLOPS**（26.3% AVX-512 理论峰值，约 84.1% 降频后峰值）
3. **AVX-512 降频是关键瓶颈**：频率从 3.2 GHz 降至约 1.0 GHz，降频幅度约 69%，抵消了向量宽度优势
4. **8×24 版本性能严重下降**：寄存器溢出导致性能仅 13.46 GFLOPS，说明微内核设计必须考虑寄存器限制
5. **AVX-512 版本中 9×16 最优**：在向量宽度利用、数据复用和寄存器压力之间取得最佳平衡
6. **小矩阵慢**是因为打包和循环开销占比大，无法被充分摊销
7. **后续方向**：多核并行、动态分块参数、缓存预取优化、混合指令策略
