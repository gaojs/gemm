# GEMM AVX2/AVX-512 版本性能分析报告

---

## 一、测试环境

| 项目 | 说明 |
|------|------|
| **平台** | Linux (Ubuntu) |
| **CPU** | Intel(R) Xeon(R) Silver 4210 CPU @ 2.20GHz |
| **核心数** | 10 物理核心 / 20 逻辑核心 |
| **最大睿频** | 3.2 GHz |
| **L1 数据缓存** | 32 KB / 核心 |
| **L2 缓存** | 1 MB / 核心 |
| **L3 缓存** | 14 MB 共享 |
| **架构** | x86-64 (Cascade Lake) |
| **SIMD支持** | SSE, SSE2, AVX, AVX2, AVX-512F/DQ/BW/VL |

**理论峰值计算**：

> FMA 指令一次完成乘法和加法，计为 2 FLOPs。每个核心有 2 个 FMA 执行单元。

- AVX2 (256位, 4 doubles): 4 doubles × 2 FMA × 2 FLOPs × 3.2 GHz = **51.2 GFLOPS**（单核心）
- AVX-512 (512位, 8 doubles): 8 doubles × 2 FMA × 2 FLOPs × 3.2 GHz = **102.4 GFLOPS**（单核心）

> **注意**：实际运行时，AVX-512 指令会导致 CPU 降频（约降至 2.2 GHz 基础频率），因此 AVX-512 实际峰值约为 **70.4 GFLOPS**（8 × 2 × 2 × 2.2 GHz）。

## 二、测试参数修改

### 2.1 parameters.h 修改内容

| 参数 | 原值 | 新值 | 说明 |
|------|------|------|------|
| `PFIRST` | 100 | **64** | 最小矩阵维度 |
| `PLAST` | 1000 | **1280** | 最大矩阵维度 |
| `PINC` | 100 | **64** | 步长 |

### 2.2 修改原因与好处

**原因**：AVX-512 微内核的列数（NR）为 8/16/32，100 不是这些数的整数倍，导致边界处理时缓冲区溢出。

**好处**：
1. **消除边界问题**：64 是 4、8、16、32 的公倍数，所有微内核版本无需边界处理代码
2. **更精细的性能曲线**：步长 64 比 100 更小，可以观察更多数据点
3. **更大矩阵测试**：1280 比 1000 大，可以看到大矩阵的缓存效应

## 三、版本修改分析

### 3.0 MMult0（基线版本）

**实现方式**：三重循环朴素矩阵乘法（i, j, p 循环）

**性能结果**：**1.51 GFLOPS**

---

### 3.1 MMult4-4x4-avx2.c（AVX2 版本，4行×4列）

**主要修改**（相对于 MMult3_4x4_15）：
- 使用 AVX2 指令集（`__m256d`，256位向量）
- 每次处理 4×4 的微内核
- 使用 `_mm256_loadu_pd` / `_mm256_storeu_pd` 加载/存储
- 分块参数：nc=128, kc=256

**性能提升原因**：
- AVX2 可同时处理 4 个 double，是 SSE2（128位）的 2 倍
- 打包 A 和 B 矩阵，提高缓存利用率

**性能结果**：**21.65 GFLOPS**（达到 AVX2 理论峰值的 **42.3%**）

---

### 3.2 MMult4-4x8-avx2.c（AVX2 版本，4行×8列）

**主要修改**（相对于 4×4 AVX2 版本）：
- 微内核从 4×4 扩展到 4×8
- 使用 FMA 指令（`_mm256_fmadd_pd`）替代乘加分离
- 直接加载/存储 C 矩阵（避免逐个元素提取）
- 动态分配打包内存（`aligned_alloc`），支持任意矩阵大小
- 分块参数：nc=128, kc=256

**性能提升原因**：
- 4×8 微内核每次循环计算 32 个元素（vs 4×4 的 16 个），数据复用率翻倍
- FMA 指令将乘法和加法合并为一条指令，减少指令数约 50%
- 直接加载/存储 C 矩阵避免了大量的逐个元素提取和累加操作
- 动态内存分配消除了栈溢出风险

**性能结果**：**36.93 GFLOPS**（达到 AVX2 理论峰值的 **72.1%**）

---

### 3.3 MMult4-4x8-avx512.c（AVX-512，4行×8列）

**主要修改**（相对于 AVX2 4×8 版本）：
- 使用 AVX-512 指令集（`__m512d`，512位向量）
- 使用 `_mm512_fmadd_pd`

**性能结果**：**23.95 GFLOPS**

> **注意**：AVX-512 版本性能低于 AVX2 版本，原因见第五章分析。

---

### 3.4 MMult4-8x8-avx512.c（AVX-512，8行×8列）

**主要修改**（相对于 4×8 版本）：
- 微内核从 4×8 扩展到 8×8
- 行方向处理 8 行，需要更多寄存器

**性能结果**：**26.51 GFLOPS**

---

### 3.5 MMult4-4x16-avx512.c（AVX-512，4行×16列）

**主要修改**（相对于 4×8 版本）：
- 微内核从 4×8 扩展到 4×16
- 使用两个 `__m512d` 处理 16 列

**性能结果**：**27.94 GFLOPS**

---

### 3.6 MMult4-4x16-avx512p.c（堆分配版本）

**主要修改**（相对于栈分配版本）：
- packedB 使用 `aligned_alloc` 动态分配（64字节对齐）
- 支持任意大小的内存需求

**性能结果**：**28.71 GFLOPS**

---

### 3.7 MMult4-4x32-avx512.c（AVX-512，4行×32列）

**主要修改**（相对于 4×16 版本）：
- 微内核从 4×16 扩展到 4×32
- 使用 4 个 `__m512d` 处理 32 列
- 编译器自动优化为 FMA 指令
- 动态内存分配
- 分块参数：nc=64, kc=1024

**性能结果**：**29.33 GFLOPS**

---

### 3.8 MMult4-4x32-avx512-nc128.c（AVX-512，nc=128）

**主要修改**（相对于 4×32 原版）：
- nc 从 64 增加到 128：更大的 B 矩阵分块，减少外层循环迭代次数
- 使用 `_mm512_fmadd_pd` 内联函数（显式 FMA）
- PackMatrixB 使用 AVX-512 加载/存储指令（`_mm512_loadu_pd` / `_mm512_store_pd`）

**性能提升原因**：
- nc=128 使 packedB 大小从 512 KB 增加到 1 MB，更好地利用 L2 缓存（1 MB/核心）
- 减少 j 循环迭代次数，降低循环开销
- PackMatrixB 使用 AVX-512 指令一次处理 32 个 double，提高打包效率

**性能结果**：**29.70 GFLOPS**（比原版提升约 1.3%）

## 四、性能对比总结

### 4.1 峰值性能对比

| 版本 | 微内核 | 分块参数 | 峰值 (GFLOPS) | 提升 | AVX2理论比例 | AVX-512理论比例 |
|------|--------|---------|--------------|------|-------------|---------------|
| MMult0 | 基线 | 无 | 1.51 | 1x | 3.0% | 1.5% |
| MMult4-4x4-avx2 | 4×4 | nc=128, kc=256 | 21.65 | 14.3x | 42.3% | -- |
| **MMult4-4x8-avx2** | **4×8** | **nc=128, kc=256** | **36.93** | **24.5x** | **72.1%** | -- |
| MMult4-4x8-avx512 | 4×8 | nc=128, kc=256 | 23.95 | 15.9x | -- | 23.4% |
| MMult4-8x8-avx512 | 8×8 | nc=128, kc=256 | 26.51 | 17.6x | -- | 25.9% |
| MMult4-4x16-avx512 | 4×16 | nc=128, kc=256 | 27.94 | 18.5x | -- | 27.3% |
| MMult4-4x16-avx512p | 4×16 | nc=128, kc=256 | 28.71 | 19.0x | -- | 28.0% |
| MMult4-4x32-avx512 | 4×32 | nc=64, kc=1024 | 29.33 | 19.4x | -- | 28.6% |
| **MMult4-4x32-avx512-nc128** | **4×32** | **nc=128, kc=1024** | **29.70** | **19.7x** | -- | **29.0%** |

> 注：AVX2 理论峰值按 51.2 GFLOPS 计算，AVX-512 理论峰值按 102.4 GFLOPS 计算。
> 若考虑 AVX-512 降频后的实际峰值（~70.4 GFLOPS），4×32-nc128 版本达到约 **42.2%**。

### 4.2 性能提升关键因素

1. **向量宽度**：AVX-512 (512位) > AVX2 (256位) > SSE (128位)
2. **微内核大小**：更大的微内核 → 更多数据复用 → 更少内存访问
3. **FMA 指令**：将乘法和加法合并，减少指令数约 50%
4. **内存对齐**：对齐加载比非对齐加载快约 5-10%
5. **分块策略**：合理的 kc/nc 分块减少缓存失效
6. **直接加载/存储 C**：避免逐个元素提取，减少冗余操作

## 五、小矩阵性能分析

### 5.1 现象

所有版本在小矩阵（如 64×64×64）时性能显著低于大矩阵。例如：
- MMult4-4x8-avx2：64×64 时 10.08 GFLOPS，448×448 时 36.93 GFLOPS（差距 3.7 倍）
- MMult4-4x32-avx512：64×64 时 6.55 GFLOPS，512×512 时 29.33 GFLOPS（差距 4.5 倍）

### 5.2 原因分析

1. **打包开销占比大**：小矩阵的打包成本（A 打包、B 打包）占总计算时间的比例更高。打包是 O(k×n) 操作，而计算是 O(m×n×k) 操作，小矩阵时打包占比显著增大。

2. **循环开销**：k 维度短时，内层循环迭代次数少，循环控制开销（分支预测、计数器更新）占比更高。

3. **缓存冷启动**：第一次访问数据时，数据不在缓存中，需要从内存加载。小矩阵的总计算量小，缓存预热成本无法被充分摊销。

4. **固定开销**：函数调用、内存分配（`aligned_alloc`/`free`）等固定开销在小矩阵时占比更高。

5. **分块颗粒度**：当前分块参数（如 kc=1024）针对大矩阵优化，小矩阵（如 k=64）无法充分利用分块的优势。

### 5.3 优化建议

- 对于小矩阵（k < 256），可以跳过打包步骤，直接使用朴素 SIMD 计算
- 动态调整分块参数：小矩阵使用更小的 kc/nc

## 六、AVX-512 性能瓶颈分析

### 6.1 为什么 AVX-512 版本性能不如 AVX2？

MMult4-4x8-avx2 达到 36.93 GFLOPS，而所有 AVX-512 版本最高仅 29.70 GFLOPS。主要原因：

1. **AVX-512 频率降频（核心原因）**：Intel Xeon Silver 4210 在执行 AVX-512 指令时，CPU 会降低时钟频率以保证功耗和散热在安全范围内。虽然 AVX-512 每条指令处理 2 倍数据，但频率下降幅度（约 30-40%）抵消了向量宽度优势。

2. **寄存器压力**：4×32 微内核使用 20 个 ZMM 寄存器（16 个累加器 + 4 个 B 向量），而 AVX-512 共 32 个寄存器。虽然未溢出，但寄存器压力较大，可能影响编译器优化。

3. **功耗墙**：AVX-512 的功耗远高于 AVX2，Intel 的"license-based"频率管理策略导致 AVX-512 代码运行在更低的频率。

### 6.2 如何进一步提升

1. **混合指令策略**：在 AVX-512 代码中适当混入 AVX2 或 SSE 指令，可能减轻降频程度
2. **多核并行**：当前测试使用单核心，10 核心并行可将性能提升近 10 倍
3. **缓存预取**：使用 `_mm_prefetch` 在计算前预取数据，隐藏内存延迟
4. **更优分块参数**：针对不同矩阵大小动态选择最优的 kc/nc
5. **使用 MKL/BLIS**：Intel MKL 或 BLIS 库经过深度优化，可达到 80%+ 的理论峰值

## 八、结论

1. **最佳 AVX2 版本**：MMult4-4x8-avx2，达到 **36.93 GFLOPS**（72.1% AVX2 理论峰值）
2. **最佳 AVX-512 版本**：MMult4-4x32-avx512-nc128，达到 **29.70 GFLOPS**（29.0% AVX-512 理论峰值，约 42.2% 降频后峰值）
3. **AVX-512 降频是关键瓶颈**：频率从 3.2 GHz 降至约 2.2 GHz，抵消了向量宽度优势
4. **小矩阵**慢是因为打包和循环开销占比大，无法被充分摊销
5. **后续方向**：多核并行、动态分块参数、缓存预取优化
